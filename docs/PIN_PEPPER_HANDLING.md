# PIN Pepper Architecture & Operational Runbook

## 1. What is the PIN Pepper and Where Does it Live?
In the Vitarak platform, staff devices (Order-Takers, Packers) authenticate with a 6-digit numerical PIN.

A 6-digit PIN has only $1,000,000$ possible combinations ($000000$ to $999999$). Even with slow algorithms like bcrypt or argon2, an attacker who obtains a database dump could brute-force the entire search space in seconds or minutes.

To prevent this:
- **`PIN_PEPPER`** is a high-entropy secret string that lives **strictly in server environment variables** (e.g. `.env` in local development; Vercel / container environment variables in production).
- It is **never** committed to version control and **never** stored in the database.
- Before hashing or verification, the 6-digit PIN is combined with the pepper using HMAC-SHA256 (`crypto.createHmac('sha256', pepper).update(pin).digest('hex')`).
- The output of the HMAC is what gets passed to bcrypt. Without the server's `PIN_PEPPER`, a leaked database alone is completely useless for cracking PINs.

---

## 2. Impact of Losing the PIN Pepper
> [!WARNING]
> **Losing `PIN_PEPPER` invalidates all registered device PINs across all tenants.**
> Because HMAC is a one-way function, if `PIN_PEPPER` is accidentally deleted or overwritten with a new value without a rotation protocol, every subsequent `bcrypt.compare` will fail.
> 
> **Recovery if lost**: The owner would have to revoke the affected devices in `/d/devices` and generate fresh single-use invite links for staff to set new PINs.

## 3. Zero-Downtime Secret Rotation Protocol
If a security audit or organizational policy requires rotating the `PIN_PEPPER`, our authentication engine ([lib/services/session.ts](file:///c:/Users/harsh/OneDrive/Desktop/Study/PROJECTS/Inventory%20and%20Sales%20Management/lib/services/session.ts)) supports **dual-pepper zero-downtime rotation**:

### Step-by-Step Rotation:
1. **Generate New Secret**: Generate a cryptographically secure 64-character random string for the new pepper.
2. **Configure Dual Peppers**: In your production environment variables:
   - Set `PIN_PEPPER = <new_secret>`
   - Set `PIN_PEPPER_OLD = <previous_secret>`
3. **Deploy**: Restart or redeploy the server.
4. **Transparent JIT Migration**:
   - When a staff member submits their 6-digit PIN, `verifyDevicePinAndUnlock` first checks against the new `PIN_PEPPER`.
   - If that does not match, it automatically checks against `PIN_PEPPER_OLD`.
   - When a match is found with `PIN_PEPPER_OLD`, the server immediately computes a new hash using `PIN_PEPPER` and updates the database row in the same transaction.
5. **Decommission Old Pepper**:
   - After an operational period (e.g., 30 days) during which active staff have unlocked their devices, remove `PIN_PEPPER_OLD` from the environment.
   - Any dormant devices that did not log in during the window can simply have a new invite generated by the distributor owner.
